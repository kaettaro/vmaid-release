# MMD(PMX / VMD / VPD)対応の検討

作成: 2026-10-14 / 状態: **検討のみ(実装していない)** / **決定(2026-10-14): アプリに MMD の直接対応は入れない。Blender での変換を案内する(§9)**

CLAUDE.md の確定事項では「モデル形式は VRM のみ。モーションは VRMA。PMX/VMD/FBX は対象外(将来拡張)」とされている。
この文書は、それを変える場合の実現可能性・方式・工数・リスクをまとめたもの。**方針の変更は、この文書をもとに本人が判断する。**

## 1. 結論(要約)

- **技術的には実現できる。** ただし「VRM のままの小さな追加」ではなく、**モデル形式を差し替えられる設計への変更**(描画まわり約680行の作り直し)が要る。
- 方式は3つ(§3)。**おすすめは「A: MMD をそのまま読み込んで再生する」を、段階的に入れる**こと。まず **VPD(ポーズ)と PMX モデルの表示**、次に **VMD(モーション)の再生**。物理(髪・服の揺れ)は最後。
- **VMD → VRM のモーション変換(C)は、品質面で難しく、おすすめしない。**
- 大きな懸念は、**技術ではなく「MMD モデルの利用条件」**(§5)。再配布禁止が多く、アプリへの同梱は不可(いまの方針どおり、利用者が自分で用意する形なら問題は小さい)。
- three.js 本体は、**r172 で MMD 関連のコードを削除済み**(いまの three 0.186.1 には無い)。外部ライブラリ `@moeru/three-mmd`(MIT・ベータ・活発に更新中)を使う。

## 2. 前提: いまの three.js には MMD が入っていない

- `three` 0.186.1 の `examples/jsm` に、`MMDLoader` / `MMDAnimationHelper` / `MMDPhysics` / `mmdparser` は**存在しない**(確認済み)。`CCDIKSolver`(IK)と `OutlineEffect`(輪郭線)だけが残っている。
- three.js のフォーラムによると、MMD 関連は r172 で削除された([discourse.threejs.org](https://discourse.threejs.org/t/mmd-modules-disappeared-after-update/87548))。「引き続き必要なら、コードをアプリ側に持つ」ことが推奨されている。
- 代替として、次の npm パッケージがある(いずれも MIT)。

| パッケージ | 状態 | 評価 |
|---|---|---|
| **`@moeru/three-mmd`** 0.2.0-beta.2 | 2026-09 更新。three ≥ 0.184 対応(いまの 0.186.1 で使える) | **第一候補**。PMD/PMX・VMD・VPD、IK、付与(grant)、トゥーン材質、物理は別パッケージ。**ベータ版**(API が変わる可能性) |
| `@moeru/three-mmd-physics-ammo` | 同上。依存 `ammojs-typed`、約1.8MB | 物理(Bullet / WebAssembly)。CSP の変更が要る(§4) |
| `@moeru/three-mmd-physics-springbone` | 同上。依存 `@pixiv/three-vrm-springbone`(いま使用中・MIT)、約12KB | **VRM と同じ揺れ物の仕組みで、MMD の物理を近似**。軽く、WebAssembly 不要。**おすすめ** |
| `mmd-parser` 1.1.4 | 2026-10 更新・MIT | パーサーのみ(自前でローダーを書く場合) |
| `three-mmd-loader` 0.0.11 | 2022 年で停止。three 0.84 向け | **使えない** |
| `babylon-mmd` | Babylon.js 用 | 別エンジン。不採用 |
| `three-stdlib` 2.36.1 | three の examples の複製(2025-11)。**旧版の `MMDLoader` / `MMDAnimationHelper` / `MMDPhysics` / `mmdparser` を含む**(パッケージの中身で確認)。物理は `ammo.js`(別途読み込み)が必要 | 次点。**three の旧版相当のコードで、three 0.186 との整合は未確認**。保守は、three-stdlib の側。`@moeru/three-mmd` が使えない場合の代替 |

## 3. 方式の比較

### A. MMD をそのまま読み込んで再生する(推奨)
PMX を `@moeru/three-mmd` で読み込み、VMD / VPD をそのモデルに適用する。VRM とは**別の「モデルの種類」**として扱う。
- 長所: MMD のモーション(VMD)が**本来の品質で**動く(IK・付与・物理を含む)。MMD 向けの膨大な既存の素材が使える。
- 短所: 描画まわりを「VRM 専用」から「モデルの種類を差し替えられる」形に作り直す必要がある(§4)。

### B. PMX を VRM に変換して取り込む
- 変換は、Blender(+ MMD Tools + VRM アドオン)など**外部ツールでの手作業**が必要。アプリ内で完結する安定した変換器は確認できていない。
- 長所: アプリは VRM のままでよい。短所: 利用者の手間が大きく、変換で表情・材質・物理が劣化する。**取り込み機能とは言えない**。
- 結論: アプリの機能にはせず、「変換したい人向けの案内」を README に書く程度が妥当。

### C. VMD を VRMA に変換して、VRM に再生する
- MMD のボーン名(センター・上半身・足IK など)を VRM のヒューマノイドに対応づけ、**IK を FK に焼き込む**必要がある。
- MMD モデルと VRM モデルは、**体の比率・ボーンの回転軸・初期ポーズ(A ポーズ / T ポーズ)が違う**ため、足が滑る・腕が体に刺さるなどが起きやすい。
- 検索では、VMD → VRMA の変換ツールは見つからなかった(Blender のリターゲット系アドオンが近いが、VRMA 出力は確認できない)。**自前実装は工数が大きく、品質を保証できない**。
- 結論: **おすすめしない。**

## 4. 方式 A の設計と工数の目安

### 4.1 変わる所・変わらない所
- **そのまま使える**(モデルの形式に依存しない): ルールエンジン、LLM・会話・履歴、設定画面、ルールの GUI、モデル管理(約4,100行)。
- **作り直す**: キャラの描画まわり 3 ファイル・約680行(`vrmStage.ts` / `characterController.ts` / `adjustLayer.ts`)。VRM 固有 API の使用は約 25 か所(表情の `expressionManager`、ヒューマノイド骨、VRMA、`rotateVRM0` など)。
- 作り方: 「キャラモデル」の共通インターフェース(表情・モーフの列挙と設定、モーション再生、骨の位置、口パク、まばたき、外形)を定め、`VrmModel` と `MmdModel` の2つの実装にする。ステージはインターフェースだけを見る。

### 4.2 機能ごとの対応(MMD での扱い)

| 機能 | MMD での扱い | 難しさ |
|---|---|---|
| モデルの表示(PMX) | `@moeru/three-mmd` の `MMDLoader` | 中(テクスチャの読み込み方が必要・§4.3) |
| 表情・衣装パネル(表情・モーフ・表示) | MMD のモーフ(表情)は、**自動列挙の方針にそのまま合う**(数百個あっても対応済み)。材質の表示切替も同じ | **低**(SPEC の「MMD 由来で数百個」の想定どおり) |
| まばたき・口パク | MMD の表情名(「まばたき」「あ」「い」…)を、内部の標準名にマッピングする | 中(日本語の表情名の対応表) |
| 触った部位 | 骨の名前が日本語(「上半身」「左ひじ」…)。**腕・手の判定**に、対応表が要る。胴体・脚は外形の割合で判定済みなので影響しない | 低 |
| モーション: VMD | `buildAnimation` + `updateWithMixer`(IK・付与を適用) | 中 |
| ポーズ: VPD | `VPDLoader` + `applyVPD`。**静止ポーズ**(テキスト形式)。実装が最も軽い | **低** |
| 内蔵モーション(自作 VRMA) | **MMD モデルには使えない**(ボーン構造が違う)。MMD 用の内蔵モーションは別に必要(待機などは VMD を自作できない) | 中〜高 |
| 待機・クリック反応などのルール | `playMotion` の名前に、VMD(または VPD)のモーションを登録する形で、そのまま動く | 低 |
| 物理(髪・スカートの揺れ) | `three-mmd-physics-springbone`(軽い・近似)か `…-ammo`(本来の Bullet・重い) | 中〜高 |
| 輪郭線・トゥーン | `MMDToonMaterial` と、three の `OutlineEffect`。見た目が VRM(MToon)と変わる | 中 |
| クリック透過の当たり判定 | いまはアルファ値で判定(描画結果から読む)。MMD でも同じ方式が使える | 低 |

### 4.3 追加で必要な技術要素
1. **テクスチャの読み込み**: PMX は、画像ファイルを**モデルのフォルダ内に別ファイルで参照**する(VRM は1ファイルに埋め込み)。いまのレンダラーは、サンドボックスで**任意のファイルを直接読めない**。
   - 対応案: main からモデルのフォルダ内の画像だけを配信する**専用のプロトコル**(例: `vmaid-model://<モデルのID>/...`)を作る。フォルダの外は配信しない(安全性の確保)。CSP の `img-src` に、このプロトコルだけを追加する。
   - 日本語のファイル名(Shift-JIS 由来)や、`toon01.bmp` などの標準トゥーン画像の扱いも必要(標準トゥーンは MMD 本体に付属していて、モデルには入っていないことが多い。**同梱するにはライセンス確認が要る**ので、自前で生成した代替トゥーンを使う案が安全)。
2. **物理エンジン(Bullet / WebAssembly)**を使う場合: CSP の `script-src` に `'wasm-unsafe-eval'` が必要になる。現在は外部通信・実行を厳しく絞っているので、**緩める範囲を最小にする**必要がある。`springbone` 方式なら、これは不要。
3. **「モデルの種類」を保存する**: 履歴や調整プロファイルは、モデルのハッシュで識別しているので、PMX(複数ファイル)では、「フォルダ全体のハッシュ」に変える必要がある。
4. **モデルの選択**: PMX は、`.pmx` を選ぶと、同じフォルダの画像を使う。`.zip` で配布されることが多いので、**zip の展開**(ライブラリ追加・パス検査が必要)をどうするか決める。

### 4.4 工数の目安(段階的に入れる場合)

| 段階 | 内容 | 目安 |
|---|---|---|
| 0 | 調査・方針決定、**実際のPMX/VMDで動作確認**(本人が用意する素材で) | 小 |
| 1 | モデルの共通インターフェース化(**VRM の動作を変えずに**描画まわりを整理) + テスト | 中 |
| 2 | PMX の表示(専用プロトコルでのテクスチャ読み込み、トゥーン・輪郭)、表情・衣装パネルの対応、まばたき・口パク | 中〜大 |
| 3 | VPD(ポーズ)と VMD(モーション)の登録・再生、ルールからの呼び出し | 中 |
| 4 | 物理(springbone 方式を優先、必要なら ammo) | 中 |
| 5 | MMD 用の内蔵モーション(待機など)・表情名の対応表・日本語の骨名の対応 | 中 |

実装者(私)の感覚では、**段階1〜3 で、PMX を表示して VPD/VMD を動かすところまでが、このアプリの M1〜M2.5 の合計に近い規模**になる。**最大の不確実性は「実際の PMX・VMD で、期待どおりに見えるか」**で、素材なしには、見積もりの精度が出ない。

## 5. 法的・運用上の注意(重要)

- **MMD モデルの利用条件は、作者ごとに違う。** 共通の標準規約は無い(検索で確認)。多くのモデルで、**再配布の禁止**、**改変の制限**、**公開の場での使用の制限**(例: VRChat での公開禁止、暴力・政治的な使用の禁止)が定められている。商用や収益化の可否も、モデルごとに違う。
- したがって、**アプリに MMD モデル・VMD を同梱してはならない**(いまの「素材は同梱しない」方針のまま)。利用者が自分で入手したものを、自己責任で使う形にする。
- `docs/TERMS.md` の「利用者が用意する素材」の条項は、PMX/VMD にもそのまま当てはまるが、**MMD 特有の注意**(配信・動画投稿の可否、改変の可否)を、追記したほうがよい。
- **VMD(モーション)にも、配布者の利用条件**がある(「モーションの再配布禁止」「使用時にクレジット」など)。本アプリのルール共有機能(書き出し)は、**モーションそのものを含まない**(名前の参照のみ)ので、問題は起きにくい。
- 取り込んだ MMD モデルを、画面上に常駐させる使い方は、「MMD で動画を作る」ことと**性質が違う**。モデルの規約が「MMD での使用」だけを許している場合、**デスクトップ常駐アプリで使うことが許されるかは、作者に確認が要る**。この点は、README にも書くのが望ましい。

## 6. 技術的なリスク

| リスク | 内容 | 対策 |
|---|---|---|
| `@moeru/three-mmd` がベータ版 | API が変わる・不具合がある可能性 | バージョンを固定し、モデルの共通インターフェースの内側に隔離する(差し替えやすくする) |
| 品質の確認ができない | 手元に PMX/VMD が無い(ライセンスの都合で、同梱・取得はできない) | **本人が持つ素材で、段階0の動作確認をしてから、本実装を決める** |
| パフォーマンス | MMD モデルは、頂点数・材質数・モーフ数が多い(物理・IK も加わる)。常駐アプリで、CPU/GPU の負荷が上がる。8GB の Mac で、LLM と同時に動かす余裕が小さい | 物理はオフにできるようにする。フレームレートの上限を設ける |
| 見た目の差 | MMD のトゥーン・輪郭・スフィアマップは、VRM(MToon)と見た目が違う | 見た目の再現度は、割り切る(完全な MMD 再現は目指さない) |
| CSP・安全性 | 専用プロトコルと、(ammo を使う場合)WebAssembly の許可 | プロトコルは、モデルのフォルダ内の画像だけ配信。ammo は使わず springbone を優先 |
| zip の展開 | 悪意あるファイルのパス(`../` など)で、意図しない場所に書き込まれる危険 | 展開先を固定し、パスを検査する(ZipSlip 対策)。**まずは zip 非対応**(展開済みのフォルダだけ)でよい |

## 7. 推奨する進め方

1. **まず、「段階0」**: 手元の PMX モデル・VMD・VPD を、1つずつ用意してもらい、`@moeru/three-mmd` の動作確認用の**使い捨ての小さなデモ**(アプリ本体は変えない)で、読み込み・見た目・IK・物理を確認する。ここで「採用するか」「どこまでやるか」を決める。
2. 採用する場合は、**段階1(VRM を変えずに共通インターフェース化)** から入れる。VRM の動作が壊れないことを、既存のテストと実機確認で担保する。
3. VPD(ポーズ)から入れて、次に VMD(モーション)に進む(軽い順)。
4. 確定事項(CLAUDE.md の「PMX/VMD/FBX は対象外」)は、**採用が決まった時点で**、理由を添えて更新する。

## 8. 判断してほしいこと

1. MMD 対応を**やるか**(やる場合は、上の段階の、どこまでを目標にするか)。
2. 「段階0」の動作確認用に、**手元の PMX / VMD / VPD**(利用条件が、個人の動作確認に問題ないもの)を使ってよいか。
3. 物理(髪・服の揺れ)を**必要とするか**(必要なら、springbone 方式で十分か、本来の Bullet が要るか)。
4. 「デスクトップ常駐」での使用が、**手元のモデルの利用条件で許されるか**(各モデルの規約の確認は、利用者の責任)。

## 9. 決定(2026-10-14): 実装せず、Blender での変換を案内する(**2026-10-16 に撤回。§10 を参照**)

本人の判断で、**アプリへの MMD(PMX/VMD)直接対応は実装しない**。MMD の素材を使いたい人には、**Blender で VRM / VRMA に変換**してから取り込む方法を案内する。CLAUDE.md の確定事項「PMX/VMD/FBX は対象外」は、変わらない。

### 確認できたこと(Blender 側)
- **モデル(PMX → VRM)**: MMD Tools で PMX を取り込み、VRM Add-on で VRM に書き出す手順が、コミュニティの複数の手順書で確認できる。そのまま書き出して動いたという報告もある一方、ボーン名の整理や材質の調整が要ることが多い。
- **モーション(VMD → VRMA)**: VRM Add-on の**公式ドキュメントに、VRMA の書き出し([Export VRM Animation (.vrma)](https://vrm-addon-for-blender.info/en-us/ui/export_scene.vrma/))の説明がある**(VRM 1.0 のアーマチュアが必要。Humanoid ボーンの回転・Hips の移動・表情のプレビュー値を書き出せる。視線は未対応)。ただし、**VMD を VRM モデルに適用する手順そのもの(リターゲット・IK の焼き込み)の公式な手順は確認できていない**。体の比率・初期ポーズ(A/T ポーズ)の違いを、手作業で調整することになる。
- VRM Add-on: Blender 2.93〜5.2 対応、ライセンスは MIT と GPL-3.0 の併記(Blender のアドオンとして使うだけで、VMaid には含まれない)。

### 注意
- 変換しても、元の素材の**利用条件は、なくならない**。改変・変換を禁止している作者もいるので、変換前に各素材の規約を確認する。
- 変換の品質は手作業に依存する(特にモーション)。
- 大量のモーションの変換は、1つずつ Blender で行うため手間がかかる。

### 再検討する条件
次のような要望が増えた場合は、§7 の段階0(使い捨てのデモでの動作確認)から、再検討する。
- Blender での変換が、利用者にとって大きな負担になっている。
- `@moeru/three-mmd` が、ベータを終えて安定した。
- 手元の素材で、デスクトップ常駐での利用が許されることが確認できた。

## 10. 決定の更新(2026-10-16): 公式の機能 Mod「MMD 対応」として実装する
§9 の「再検討する条件」のうち、「Blender での変換が、利用者の大きな負担になっている」に当たると判断し、**PMX・VMD(と VPD)を、公式の機能 Mod として実装する**(`docs/adr/0005-mod-centered-design.md`、計画 M12)。
- 段階 0(使い捨てのデモでの動作確認)は完了: `@moeru/three-mmd` 0.2.0-beta.2(MIT)・three 0.186.1 で、PMX(26MB・360 ボーン)の読み込み、VMD、IK、Bullet 物理(ammo、約 53fps)が動いた。ストッキングの穴は、全材質の `alphaTest = 0.01` で解消した。
- Mod が OFF のときは、MMD のコード(`@moeru/three-mmd`・ammo)を読み込まない(動的 import)。
- 未確認: 実際の CSP の下での ammo(WebAssembly)の要否、スカートの縁の見え方。素材は同梱しない。
- §9 の Blender での変換の手順は、MMD 対応 Mod が完成するまでの暫定の案内として残す。
- 実装(M12、2026-10-16): 公式の機能 Mod「MMD 対応」(`mmd`)。PMX は `vmaid-model://` 専用プロトコル(モデルのフォルダの中の、モデル・画像だけを配信。シンボリックリンクでの脱出を拒否)で読み、VMD は取り込み時に形式を確かめて、そのまま登録する。MMD のコード(`@moeru/three-mmd`・ammo)は、PMX を読むときだけ動的に読み込む。実アプリ(CSP 下)で、ammo の物理が、`'wasm-unsafe-eval'` なしで動くことを確認した。

- 形式インポーター(M14): FBX のモーション変換と、FBX・PMX の小道具を、別の機能 Mod として実装した(`docs/SPEC.md` §13)。`.x` 形式は、2026-10-16 時点で、three.js 用の MIT 等のローダーを検索で確認できず、**未確認**のため見送り(PMX の小道具を先に出した)。
- **方針の転換(2026-10-17): VMD → VRMA の変換を、公式の機能 Mod「VMD インポーター」(`vmd-import`)として実装した**(§3-C の「おすすめしない」は、この日付で改める)。理由: BVH → VRMA の変換(`bvhRetarget.ts`)という、使い回せる土台があること、体の VMD と表情の VMD が別ファイルのことが多く、Blender での手作業が利用者の負担だったこと。
  - 作り: 自前の VMD パーサ(`vmdParse.ts`)→ 標準 MMD 骨格のテンプレート(`mmdSkeleton.ts`。手元の標準的な PMX から骨の位置・IK の定義を実測して固定。素材は含まない)で、30fps にサンプリングして FK + 足 IK(`vmdSolve.ts`。脚は、ひざの角度を距離で決める解析解。CCD は、ひざがほとんど曲がらず収束しなかったため)→ 世界回転から VRM のボーンの局所回転へ(`vmdToVrma.ts`。A ポーズ → T ポーズの補正は、BVH と同じ)→ 表情(`mmd/morphToVrm.ts`)→ VRMA(`builder.ts` の expression トラック)。
  - 実ファイルでの確認: 手元の実際の VMD(約 90 秒のダンス)が、約 0.3 秒で変換でき、VRM のモデルで、足が接地したまま踊った。別ツールで変換した VRMA と比べると、腰は一致し、腕・脚は約 15〜20°のずれがあった(腕の基準の角度の違いによる。設定で変えられる)。
  - 未対応・限界: 捩り・付与は、世界回転に含まれる範囲だけ(補助ボーンは使わない)。髪・小物の骨・物理は使わない。モデルが標準の MMD 骨格と大きく違うモーションは崩れうる。ウィンクの左右は、モデルによって逆のことがある。IK が届かないフレームは、足を伸ばしきる(件数を変換結果に出す)。
